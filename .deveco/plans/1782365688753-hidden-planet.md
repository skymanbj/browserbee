# 添加图片/文件上传功能 — 实施计划

## Goal

为 BrowserBee 的聊天输入框增加附件上传功能，让用户可以在发送 prompt 时附带图片、PDF 和文本文件，这些附件会作为多模态内容发送给 LLM 进行分析。

## Scope / Non-goals

**包含：**
- 用户通过按钮点击、拖拽、Ctrl+V 粘贴上传文件
- 支持图片（PNG/JPG/GIF/WebP）、PDF、文本文件（TXT/MD/CSV/JSON 等）
- 所有 5 个 LLM 提供商（Anthropic、OpenAI、Gemini、Ollama、OpenAI-Compatible）支持接收图片
- 文本文件读取内容后以纯文本形式发送给 LLM
- PDF 以 base64 图片形式发送（若 LLM 支持）或提取文本发送
- 附件预览（缩略图/文件名显示）和删除
- 聊天消息中展示用户上传的附件

**不包含：**
- 修复 Agent 截图发给 LLM 的问题（保持现状：只发文字引用）
- 视频或音频文件支持
- 文件持久化存储（仅当前会话有效）
- 对不支持图片的模型的运行时拦截（仅 UI 提示）

## Current State And Constraints

### 现有消息流
1. 用户在 `PromptForm` 输入文本 → `SidePanel.handleSubmit(prompt)` → `useChromeMessaging.executePrompt(prompt)` → `chrome.runtime.sendMessage({ action: 'executePrompt', prompt })`
2. Background `messageHandler` → `agentController.executePrompt(prompt)` → 将 `{ role: "user", content: prompt }` (纯字符串) 加入历史
3. `ExecutionEngine` 用消息历史调用 `LLMProvider.createMessage(systemPrompt, messages, tools)`
4. 各提供商直接将 `msg.content` 当作字符串传递

### 关键约束
- **Chrome Extension Service Worker** 没有 DOM，不能直接使用 `FileReader`；文件读取必须在 sidepanel 中完成
- **Chrome 消息大小限制**：`chrome.runtime.sendMessage` 单条消息约 64MB，但大图片 base64 可能很大，需要压缩
- **消息类型统一**：所有提供商当前用 `GenericMessage { role, content: string }` 存储历史，需改为支持 `content: string | ContentBlock[]`
- **Gemini 提供商** 当前把所有 content 强制转 `parts: [{ text: string }]`，需要大幅改造

### 各提供商多模态格式

| 提供商 | 图片格式 | PDF 格式 |
|--------|---------|---------|
| **Anthropic** | `{ type: "image", source: { type: "base64", media_type, data } }` | 不支持原生 PDF，需提取文本 |
| **OpenAI** | `{ type: "image_url", image_url: { url: "data:MIME;base64,DATA" } }` | 同上 |
| **Gemini** | `{ inline_data: { mime_type, data } }` (在 parts 数组中) | 同上 |
| **Ollama** | `images: [base64Data]` 字段 或 data URI 内联 | 同上 |
| **OpenAI-Compatible** | 同 OpenAI 格式 | 同上 |

## Design

### 1. 附件数据类型定义

在 `src/sidepanel/types.ts` 中新增：

```typescript
// 附件类型
export type AttachmentType = 'image' | 'pdf' | 'text';

export interface FileAttachment {
  id: string;             // 唯一标识，用于删除
  name: string;           // 文件名
  type: AttachmentType;   // 附件类别
  mimeType: string;       // 原始 MIME 类型
  data: string;           // base64 编码数据（图片/PDF）或纯文本内容（文本文件）
  size: number;           // 文件大小（字节）
  thumbnail?: string;     // 图片缩略图（用于预览，仅图片类型）
}
```

在 `src/background/types.ts` 中修改 `ExecutePromptMessage`：

```typescript
export interface ExecutePromptMessage {
  action: 'executePrompt';
  prompt: string;
  attachments?: FileAttachment[];  // 新增
  tabId?: number;
  windowId?: number;
}
```

同时需要共享 `FileAttachment` 类型——将附件类型定义提取到 `src/shared/types.ts` 或直接在 `background/types.ts` 中定义并从 sidepanel 引用。

### 2. 文件读取与处理工具函数

新建 `src/sidepanel/utils/fileUtils.ts`：

- `readFileAsDataUrl(file: File): Promise<string>` — 用 FileReader 读取为 data URL
- `readFileAsText(file: File): Promise<string>` — 读取文本文件内容
- `processFile(file: File): Promise<FileAttachment>` — 根据 MIME 类型分发处理
- `compressImage(dataUrl: string, maxWidth: number, quality: number): Promise<string>` — 用 Canvas 压缩大图（限宽 2048px，quality 0.8）
- `generateThumbnail(dataUrl: string, size: number): Promise<string>` — 生成缩略图用于预览
- `isImageMime(mime: string): boolean`
- `isPdfMime(mime: string): boolean`
- `isTextMime(mime: string): boolean`
- `getAcceptedFileTypes(): string` — 返回 accept 属性值 `"image/*,.pdf,.txt,.md,.csv,.json,.xml,.html,.css,.js,.ts"`

图片压缩策略：超过 2048px 宽度的图片缩放到 2048px，JPEG quality 0.8，目标控制在 2MB 以内。

PDF 处理策略：PDF 文件以 base64 发送给支持 PDF 的 LLM（Gemini 原生支持），对于不支持的提供商，仅发送文件名和提示信息。

文本文件处理策略：直接读取文本内容，以纯文本块发送（不 base64 编码）。

### 3. 改造所有 LLM 提供商支持多模态消息

核心改动：将 `GenericMessage.content` 从 `string` 扩展为 `string | ContentBlock[]`，各提供商检测 content 类型并相应处理。

#### 3.1 定义通用内容块类型

在 `src/background/types.ts` 中：

```typescript
export interface TextContentBlock {
  type: 'text';
  text: string;
}

export interface ImageContentBlock {
  type: 'image';
  data: string;       // base64
  mimeType: string;   // e.g. 'image/png'
}

export interface PdfContentBlock {
  type: 'pdf';
  data: string;       // base64
  name: string;       // 文件名
}

export type ContentBlock = TextContentBlock | ImageContentBlock | PdfContentBlock;

// 修改 GenericMessage
interface GenericMessage {
  role: string;
  content: string | ContentBlock[];
}
```

#### 3.2 Anthropic 提供商改造

在 `anthropic.ts` 的消息转换中，当 `msg.content` 是数组时：
- `TextContentBlock` → `{ type: "text", text: block.text }`
- `ImageContentBlock` → `{ type: "image", source: { type: "base64", media_type: block.mimeType, data: block.data } }`
- `PdfContentBlock` → 转为 `{ type: "text", text: "[PDF file: {name} - content cannot be displayed]" }`

已有的 cache_control 逻辑需适配数组格式（已部分支持）。

#### 3.3 OpenAI 提供商改造

在 `openai.ts` 的消息转换中，当 `msg.content` 是数组时：
- `TextContentBlock` → `{ type: "text", text: block.text }`
- `ImageContentBlock` → `{ type: "image_url", image_url: { url: "data:{mimeType};base64,{data}", detail: "auto" } }`
- `PdfContentBlock` → 转为文本提示

#### 3.4 Gemini 提供商改造（重点改造）

当前 Gemini 强制 `parts: [{ text: msg.content }]`，需改为：
- 检测 `msg.content` 是否为数组
- 若是数组，遍历 `ContentBlock[]`：
  - `TextContentBlock` → `{ text: block.text }`
  - `ImageContentBlock` → `{ inline_data: { mime_type: block.mimeType, data: block.data } }`
  - `PdfContentBlock` → `{ inline_data: { mime_type: "application/pdf", data: block.data } }`（Gemini 原生支持 PDF）
- 若是字符串，保持现有行为
- 连续同角色消息合并逻辑需适配数组格式

#### 3.5 Ollama 提供商改造

修改 `ollama-format.ts`：
- `ImageContentBlock` → 提取 base64 data 放入 `images` 数组字段
- `TextContentBlock` → 文本内容
- `PdfContentBlock` → 提取文本提示

#### 3.6 OpenAI-Compatible 提供商改造

同 OpenAI 格式（pass-through），自然支持。

### 4. 改造 ExecutionEngine

在 `ExecutionEngine.ts` 中，当前用户消息总是 `{ role: "user", content: prompt }` (字符串)。

需要修改为：如果用户消息的 content 是数组（带附件），直接传递数组，不做强制转字符串。

具体改动点：
- `executePromptWithFallback()` 方法接收的 `prompt` 参数需扩展为支持附件
- 或者在 `agentController` 中将带附件的用户消息构造好（content 为 ContentBlock[]），直接传入历史

**选择方案**：在 `agentController.executePrompt()` 中构造带附件的用户消息（ContentBlock[]），存入历史，ExecutionEngine 不需要感知附件——它只是把 history 中的消息原样传给 provider。

### 5. 改造 agentController

修改 `executePrompt(prompt, tabId, isReflectionPrompt)` → `executePrompt(prompt, tabId, isReflectionPrompt, attachments?)`：

- 如果有 attachments，构造 ContentBlock[]：
  ```typescript
  const contentBlocks: ContentBlock[] = [];
  // 先添加文本 prompt
  contentBlocks.push({ type: 'text', text: prompt });
  // 添加附件
  for (const att of attachments) {
    if (att.type === 'image') {
      contentBlocks.push({ type: 'image', data: att.data, mimeType: att.mimeType });
    } else if (att.type === 'pdf') {
      contentBlocks.push({ type: 'pdf', data: att.data, name: att.name });
    } else if (att.type === 'text') {
      contentBlocks.push({ type: 'text', text: `[File: ${att.name}]\n${att.data}` });
    }
  }
  // 存入历史
  await addToConversationHistory(targetTabId, { role: "user", content: contentBlocks });
  ```

- 修改 `ChromeMessage` 类型，`ExecutePromptMessage` 增加 `attachments` 字段

### 6. 改造消息类型与 Chrome 消息协议

#### 6.1 `src/sidepanel/types.ts`

- 新增 `FileAttachment` 接口（或从共享位置导入）
- `Message` 接口增加 `attachments?: FileAttachment[]` 字段

#### 6.2 `src/background/types.ts`

- `ExecutePromptMessage` 增加 `attachments?: FileAttachment[]`
- 新增 `ContentBlock` 系列类型
- `GenericMessage.content` 类型从 `string | any` 改为 `string | ContentBlock[]`
- `UpdateOutputMessage` 等现有类型不需要改（附件信息在 Message 层面处理）

#### 6.3 Chrome 消息大小考虑

大图片 base64 可能很大。策略：
- 在 sidepanel 中压缩图片后再发送（限宽 2048px）
- 如果压缩后仍超过 4MB，警告用户
- Chrome `runtime.sendMessage` 理论上限约 64MB，4MB 以内的图片应该没问题

### 7. 改造 PromptForm UI

#### 7.1 添加附件按钮

在 textarea 左侧添加一个 📎 附件按钮（使用 FontAwesome `faPaperclip` 图标），点击触发隐藏的 `<input type="file" multiple accept="image/*,.pdf,.txt,.md,.csv,.json,...">`。

#### 7.2 拖拽支持

在 `PromptForm` 容器上添加 `onDragOver`、`onDragEnter`、`onDragLeave`、`onDrop` 事件处理：
- 拖拽进入时显示高亮边框
- 释放时读取文件并添加到附件列表

#### 7.3 粘贴支持

在 textarea 上添加 `onPaste` 事件处理：
- 检查 `e.clipboardData.items` 中是否有 `image/*` 类型的项
- 如果有，读取为 File 并处理

#### 7.4 附件预览区

在 textarea 上方、快捷指令下方添加附件预览区：
- **图片**：显示缩略图（80x80），悬停显示文件名和大小，点击 × 删除
- **PDF/文本文件**：显示文件图标 + 文件名 + 大小，点击 × 删除

### 8. 改造消息展示组件

#### 8.1 `MessageDisplay.tsx`

在渲染用户 prompt 消息（`New prompt: "..."` 系统消息）时，如果该消息有 `attachments`，在文字下方展示附件：
- 图片：小缩略图，点击可放大（简单 modal）
- 文件：文件名标签

#### 8.2 新建 `AttachmentPreview.tsx` 组件

用于消息中的附件展示：
- 图片附件：渲染 `<img>` with data URI，max-height 200px
- 文件附件：显示文件名和类型图标

#### 8.3 `ScreenshotMessage.tsx` 可复用

现有的 `ScreenshotMessage` 已有图片渲染逻辑，可以参考其样式。

### 9. 获取模型是否支持图片

在 `SidePanel` 中需要知道当前模型是否支持图片，以便在 PromptForm 中显示提示。

从 `ProviderSelector` 或 `chrome.storage.sync` 读取当前 provider/model 配置，查找 `ModelInfo.supportsImages` 标志，传递给 `PromptForm`。

当模型不支持图片时，附件按钮仍可用，但显示提示："当前模型可能不支持图片输入"。

## Risks And Compatibility

1. **Gemini 提供商改造复杂**：当前 Gemini 的消息合并逻辑强制转文本，改动量大，可能引入回归。缓解：充分测试纯文本消息在 Gemini 下的行为不变。
2. **Ollama 视觉模型不确定**：Ollama 的 `supportsImages` 当前硬编码为 false，用户需自行运行视觉模型（如 llava）。UI 会提示但不会阻止。
3. **大文件性能**：多张大图片 base64 可能导致消息体积暴增、token 消耗高。缓解：强制压缩图片，限制附件数量（最多 5 个），提示用户。
4. **PDF 兼容性**：只有 Gemini 原生支持 PDF 输入，其他提供商会退化为文本提示。需在 UI 明确提示。
5. **Chrome 消息大小**：极端情况下压缩后的图片仍可能很大。缓解：4MB 上限检查 + 警告。
6. **向后兼容**：`GenericMessage.content` 从 `string` 扩展为 `string | ContentBlock[]`，所有读取 content 的代码需兼容两种格式。`convertMessagesToProviderFormat` 需逐一检查。

## Rollback

所有改动在 `feature/add-file-attachments` 分支上进行。如果需要回滚：

1. `git checkout main` — 切回主分支
2. `git branch -D feature/add-file-attachments` — 删除功能分支
3. 新增的文件（`fileUtils.ts`、`AttachmentPreview.tsx`）直接删除
4. 修改的文件通过 `git diff main` 逐一审查或 `git checkout main -- <file>` 还原

由于是独立分支，回滚风险极低——不影响 main 分支的任何代码。
